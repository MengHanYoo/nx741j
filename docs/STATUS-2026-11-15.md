## Pandora driver port (`0022-sweet-ufs-port.patch`)

* Device-tree lookup tries `/soc/ufshc@1d84000`, `/sweet-ufs`, `/arm-io/ufshc`;
  on this unit only `/arm-io/ufshc` exists and its `reg` is **truncated**
  (`0xd84000` instead of `0x1d84000`), so the driver falls back to the real base
  and says so in the log.
* DMA allocation: `kmem_alloc_contig` of 80 KiB succeeds
  (`kr=0 va=…d000 dma pa=b4a26000`). A 1 MiB allocation hangs inside the call
  when made from the IOKit matching context, which is why the bounce buffer was
  reduced to 64 KiB.
* Cache maintenance: `flush_dcache64(addr, len, is_physical)` must be called with
  the kernel VA and `FALSE`; the original port passed the physical address with
  `TRUE`, which hangs.
* Takeover installs **our own** request list and verifies it:

```
NX741J UFS: takeover rc=0 utrlba=b4a26000 rsr=00000001 dbr=00000000
```

## The remaining blocker: the doorbell store

With the list running (`rsr=1`) the very next command hangs:

```
SWEET UFS: building cmd 0x1b lun 0xd0 len 0
SWEET UFS: synced, ringing hcs=0000010f dbr=00000000
<no "ringed" line: write32(hc, 0x58, 1) never returns>
```

Control experiments that bound the problem:

| Experiment | Result |
|---|---|
| `native-ufs-keepqueue=1` (list left stopped, `rsr=0`) | doorbell store **returns** (`ocs=0f`), nothing executes |
| `native-ufs-keepqueue=2` (start the firmware list, ring) | store hangs |
| own DMA list instead of the firmware list | store hangs |
| SMMU bypass written by hand | no change (SMMU is off anyway) |
| MCQ disabled (`memcfg=0`) | no change |
| skip `DME_HIBERNATE_EXIT` (it returns `0x101` here) | no change |
| AHB/UniPro branches forced on | no change |

So every software-side hypothesis has been excluded by a measurement: the
controller stalls when it has to fetch a descriptor from DRAM. On the pandora
device the same store works, and its boot chain reaches XNU through
`fastboot boot` from ABL, while ours goes ABL -> efisp loader -> Mu UEFI ->
DarwinBoot -> XNU, and Mu's own UFS driver has already driven the controller.
The next thing to check is therefore the state Mu leaves behind (XPU protection
of the UFS master, or a controller/NOC state that only a full HCE reset clears).

## Log channel (used ~13 times today)

`0021` mirrors the console into a DRAM buffer; `loader/p7.c` scans the GCD map,
picks the longest `NXLOG1` buffer, writes `NXLGST1` + text to `rawdump`;
`flash-boota-9008.ps1 -ReadTo` reads it. Entering 9008 re-initialises DDR, so the
loader must run between the crash and EDL. `printf` output is captured; panic()
is not (it does not go through `console_printbuf_putc`).

## Late addendum (23:25-23:50) — link state and doorbell granularity

The probe now prints its results with `panic()` so they appear in the large font
(the console text is unreadable on this panel, photographs of it are useless).

```
NX741J UFS
cap=d5c7031f hcs=0000010f hce=00000001
utrlba=b4a26000 rsr=00000001 dbr=00000000
dme done=1 res=00000000 arg3=00000002
is=00000400 memcfg=00000000
```

* `DME_GET PA_PWRMode (0x1561)` **completes** (`done=1`, UIC result code 0) and
  returns `arg3 = 0x00000002`: the link is in **SLOW**, not HIBERN8 (`0x03`).
  That is why `DME_HIBERNATE_EXIT` came back `0x101` — there was nothing to wake.
  UIC/UniPro is therefore healthy; the problem is on the host fetch side.
* Writing `UTRLDBR` itself is fine: with `IE=0`, `IS` cleared and a DSB, the
  store of **0** to `0x58` returns and reads back 0
  (`write0=00000000 before=00000000`).
* A store that sets any slot bit does **not** return: the host then fetches that
  UTRD from `UTRLBA` and the bus stalls.  (`0xFFFFFFFE` was tried first and also
  stalled, but that value asks for slots 1..31, which are not set up, so it was
  not a clean test.)
* The DMA retry-under-1 GiB experiment was being wired up when the kernel build
  started failing on the `sweet_ufs.c` translation unit; the error text is lost in
  the interleaved parallel log.  Next step: run the kernel step with `-j1` (or
  capture the per-TU log) to get the message, then finish the low-PA test.
