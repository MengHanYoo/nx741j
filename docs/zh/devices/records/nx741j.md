### 操作步骤

- cd UniXNU &amp;&amp; ./unixnu defconfig nx741j_defconfig -D ../UniXNU-nx741j

### 当前范围

- FDF [FV.FvMain] now packs UniXNURamDiskDxe directly after UniXNUDxe (Depex TRUE, produces BlockIo and DevicePath)

### 操作步骤

- ./unixnu build firmware -D ../UniXNU-nx741j   (UEFI tree from unixnu.local.toml [build] uefi)
- flash the resulting FD through a boot image or the EDL path
- inspect the FV with the firmware build log and the FFS directory under Build/nx741jPkg

### 开发经验

- UniXNURamDiskDxe was listed in the DSC but missing from the FDF, so the payload volume never got a block device; the FDF entry was added and the firmware rebuilds with it.
- AdvancedLogDxe is packed: the DSC maps AssertLib, AdvancedLoggerAccessLib, AdvancedLoggerHdwPortLib and QrEncoderLib plus DebugLib=BaseDebugLibAdvancedLogger, and the FDF carries the driver, so Tools -&gt; Advanced Logger pages the firmware log as QR frames.
- The SEC phase keeps BaseDebugLibSerialPort because SiliciumPkg/Sec/Sec.c calls BaseDebugLibSerialPortConstructor() directly; PEI and DXE use the Advanced Logger, which mirrors to the same SerialPortLib so the panel still shows the log.
- The layer 1 boot image that reached the panel carried firmware volume 2f8bc430; the later build db122c8a did not come up, so the FD version is a variable that has to be bisected. The current build is 7d820bcb.

### 完成条件

- SILICIUM_UEFI.fd builds and contains UniXNU, DarwinBoot, the ramdisk block driver and the log exporter
- firmware reaches the UniXNU menu, the payload volume is visible as a block device, and Tools -&gt; Advanced Logger exports the log as QR frames

### 当前范围

- Layer 2 stops at RpmhDxe FAR=0x58 and a TzDxeLA assertion: SMEM contents, the DTB extension and tzapps are missing ABL environment inputs
- SMEM reads back as zeros, so the DXE chain cannot be validated past the RPMh stage

### 完成条件

- Every failed stage leaves a log with the failing target and a reproducible command
- Recovery from a bad boot image restores a booting device

### 下一步

- Static trust cache 087-86593-047.dmg.trustcache with SHA-256 9cc478fe accepted by the payload
- Chip id 207 and a non-zero unique chip id for the ADT platform identity
- AMFI runs in platform code policy through /chosen/amfi-only-platform-code

### 配置

- board.toml [payload] trust_cache_sha256 lists the two accepted hashes; the local input points at the extracted trust cache
- board.toml [payload.adt] chip_id 207 and unique_chip_id required
- SoftwareAES selected so the arch archive list resolves and the AES bindings come from source

### 操作步骤

- compare payload.json trust_cache_sha256 with the board list after every build
- keep a non-zero unique chip id in the local build inputs for payload packaging

### 开发经验

- The trust cache and the ADT identity are already enforced by the payload build; a mismatch fails the build rather than the device.
- early_security_init stays empty because the original AMFI initializer address in this kernelcache has not been identified, so the early initializer does not run.

### 完成条件

- Trust cache and ADT identity match the device and the kernel reaches the early security stage
