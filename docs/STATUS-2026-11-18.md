# Status — 2026-11-18 (UFS: the stall is gone, the host still will not consume the doorbell)

Continues docs/STATUS-2026-11-17.md. Everything below is measured on the unit;
log lines come from the console buffer through `flash-boota-9008.ps1 -ReadTo`.

## 1. The bus stall had a cause, and it is fixed

The bootloader left this unit's `apps_smmu` without a match entry for the UFS
stream.  Read with the data-a-live method (`SMR(n)=0x800+4n`, `S2CR(n)=0xc00+4n`,
SMR bit31 VALID, [14:0] ID, [29:16] MASK):

```
smr[0] = 00000060   (valid=0, id=0x60, mask=0)   s2cr[0] = 00020000  (type=2 fault)
smr[1] = 00000540   (valid=0)                    s2cr[1] = 00020001
smr[2] = 80020800   (valid=1, id=0x800)          s2cr[2] = 00000002  (display)
```

Unmatched streams are faulted because `sCR0` has USFCFG set, so every UFS DMA
transaction was killed and the interconnect stalled — which is why a store of 0
to `UTRLDBR` returned while any store that set a slot never returned.

Writing the state data-a-live's bootloader already leaves:

```
SMR[0]  = 0x80000060   (VALID | id 0x60 | mask 0)
S2CR[0] = 1            (bypass)
```

makes the doorbell return:

```
NX741J UFS: stream 0x60 smr=80000060 s2cr=00000001
SWEET UFS: ringed cmd 0x1b dbr=00000001 is=00000000
```

So the earlier "write 0x58 hangs the bus" is gone; the doorbell write itself is
fine once the stream is matched.

## 2. Device side is healthy

```
DME_GET PA_PWRMode  -> done=1 res=0 arg3=00000002   (SLOW)
DME_SET PA_PWRMode=1 -> done=1 res=0                (FAST accepted)
HCS=0000010f   (DP, UTRLRDY, UCRDY)   HCE=1   MEM_CFG=0   MCQ_CFG=0x1f00
```

## 3. The remaining fact: the host never fetches the UTRD

Same descriptor, three placements, always `DBR` stays set and nothing happens:

| list location | result |
|---|---|
| our `kmem_alloc_contig` block (`0xb4a0_xxxx`) | `dbr=00000001` |
| the bootloader's own region (`0xc3b0_xxxx`, per-page mapping + 4-byte writes) | `dbr=00000001` |
| `UTRLRSR` readback | `1`, `HCS.UTRLRDY=1`, `UTRLBA` readback matches |

`HCE` reset cannot be used to recover the controller: after `HCE=0/1` the host
stops answering (no `after hce` line is ever printed; earlier runs also left
`HCS 0x10f -> 0x08`).  So the sequence "reset, DME_LINKSTARTUP, ring" cannot be
completed on this unit.

## 4. Hypotheses checked against the spec and rejected

| Hypothesis | Check | Result |
|---|---|---|
| controller is MCQ-only, legacy doorbell removed | `CAP` bits per `include/ufs/ufshci.h`: `MASK_LSDB_SUPPORT=0x20000000`, `MASK_MCQ_SUPPORT=0x40000000` | `CAP=0xd5c7031f` -> bit29=0 (legacy **supported**), bit30=1 -> rejected |
| descriptor encoding wrong | bit-by-bit against `struct request_desc_header` / `utp_transfer_req_desc` | interrupt bit24, DD bits25-26, command_type bits28-31, OCS at DW2 byte0, UCD DW4-5, response offset/length DW6, PRDT DW7 — **no difference** |
| firmware changed the controller | ABL snapshot vs kernel values (`HCS/HCE/RSR/MEM_CFG`) | identical |
| stream bypass enough | set and read back | bypass confirmed, still not consumed |

## 5. SMMU context banks are not reachable, from either world

```
kernel  : read 0x15010000 -> external abort
firmware: NX741J mu: cb read ok never printed; Synchronous Exception
          FAR=0x0000000015010000 FSR=0x96000010
```

and the firmware memory map the loader sees has **no descriptor covering
0x15000000** (`GCDSMMU1: descriptors=108 matches=0`), while the device tree
declares `reg = <0x0 0x15000000 0x0 0x100000>` and lists **no clocks or
power-domains** for `apps-smmu`.  So the CB window is blocked below the driver
level; the IOVA-0 design cannot be completed from XNU.

## 6. Where this leaves the port

UFS is blocked by the host controller not consuming requests, after every
software-visible cause has been measured and excluded.  The remaining
possibilities need vendor information (XPU/DAUS permission tables live in the
closed `QTISECLIB`; the ATF `qti_msm_xpu_bypass()` is only a stub) or a boot
chain that never lets the firmware drive UFS (data-a-live uses `fastboot boot`,
our payload is 64 MiB and cannot fit the 3 MiB efisp slot, so the firmware must
read it from UFS).

Nothing in this document depends on the experimental probes staying in tree; the
probe sources (`bsd/dev/native_ufs_iova.c`, the bypass/DME_SET block in
`0022`) are kept because each one is the evidence for a row above.

## 7. TZ answers: the SMMU context banks are xPU-protected

The vendor SCM interface in the firmware tree
(`Silicon/Qualcomm/QcomPkg/Include/Protocol/scm_sip_interface.h`) documents the
calls that can touch xPU-protected memory from the non-secure world:

```
TZ_CONFIG_XPU_VIOLATION_ERR_FATAL  0x02000C0E  param_id 2
    arg0: ENABLE(0) / DISABLE(1) / NOOP(2)      reply: enabled
TZ_IO_ACCESS_READ                  0x02000501  param_id 1
    arg0: address                              reply: value
    "Implementation takes place entirely in Monitor mode"
```

Called from the kernel through a minimal `smc #0` wrapper (`probe=37`):

```
NX741J xpu: violation_err_fatal rc=-2 enabled=0
NX741J xpu: io_read gfsr      rc=-2147483647 (0xFFFFFFFF80000001) value=0
NX741J xpu: io_read cb0_sctlr rc=-2147483647 value=0
NX741J xpu: io_read cb0_ttbr0 rc=-2147483647 value=0
```

* the SMC path itself works (TZ answers, no exception at `smc #0`), so the call
  convention is right;
* the fatal-violation query returns `E_NOT_SUPPORTED` — TZ keeps that policy to
  itself;
* every `TZ_IO_ACCESS_READ` of the context-bank page is refused with
  `0xFFFFFFFF80000001`, i.e. **TZ will not proxy these registers to HLOS at all**.

Combined with §5 (the same page aborts from XNU *and* from the firmware), the
conclusion is that the SMMU context-bank window is xPU-protected and cannot be
programmed from the non-secure world, by any route available to us.

## 8. Consequence for the port

The UFS controller needs its SMMU context bank (stream 0x60) to fetch requests.
That bank is unreachable for HLOS, and the bootloader's own pass-through state
is not preserved by the time XNU runs (the stream match entry is gone).  Driving
UFS from XNU on this unit is therefore blocked at the platform/TZ level, not at
the driver level.

Options left, both out of scope for a driver change:

1. have the firmware (Mu) mount the root volume before hand-off and pass it to
   XNU, so HLOS never touches the controller;
2. obtain a TZ configuration (or vendor XPU table) that leaves stream 0x60
   matched and bypassed for HLOS.

## 9. Mu is not the culprit

`UfsPassThruDxe` was removed from the firmware (`MdeModulePkg.dsc`), the FD
rebuilt (4 MiB, no `UfsPassThru` strings) and flashed together with the probe
payload.  The kernel behaved exactly as before:

```
NX741J UFS: takeover rc=0 utrlba=b4a07000 rsr=00000001 dbr=00000000
NX741J UFS: dme_set FAST done=1 res=00000000 is=00000400
SWEET UFS: ringed cmd 0x1b dbr=00000001 is=00000000
```

The doorbell is still not consumed.  So the state that keeps HLOS from driving
the controller is established **before** the firmware runs, i.e. by XBL/ABL or
by TZ.

## 10. `xbl_config.img` is a signed MBN, not editable configuration

The stock partition image from the vendor dump:

```
ELF64, Type EXEC, Entry 0x1494E000, 7 program headers, 0 sections
"EnableUfsIOC"                  appears once
"UfsSmmuConfigForOtherBootDev"  appears once
```

Both names sit in a NUL-separated **schema table**; the actual values are not a
separate table in the file.  Changing them needs a Qualcomm MBN signature, which
only the vendor can produce.

A full scan of `NX741_unlock/` (firehose programmer, `xbl_sc.elf`,
`signed_firmware_soc_view.elf`, `tme_config.elf`, `xbl_config_devprg.elf`, and
the modified `linuxloader_unlock.efi`) finds **zero** occurrences of the key,
so that package offers no way to change the UFS SMMU configuration either.

## 11. `fastboot boot` on this unit needs an EFI image

Booting our first standalone image (raw arm64 `Image` with the payload
embedded, built by `bootshim/build.sh`) produced:

```
Sending 'boot.img' (53164 KB)   OKAY
Booting                         FAILED (remote: 'No EFI image found in boot.img')
```

The ABL on this device looks for a PE/EFI application in the kernel field.  The
images that did boot this way in earlier sessions were
`gzip(shim.bin + SILICIUM_UEFI.fd)` (see `wsl/build_big.sh`), i.e. a PE shim
that enters the firmware.  A standalone UEFI-free loader therefore has to be a
PE as well, and the payload has to travel in the ramdisk field.

## 12. Final position

| Layer | Finding |
|---|---|
| XNU driver | complete: queue ownership, readback, doorbell, stream bypass, DME_FAST all verified |
| firmware (Mu) | excluded by §9 |
| bootloader config | signed MBN, key schema only, values not editable (§10) |
| TZ / xPU | context-bank page refused to XNU, to Mu and through `TZ_IO_ACCESS_READ` (§7) |

Driving UFS from HLOS on this unit needs a vendor-signed XBL/TZ change.  There is
no driver-side work left, and no boot-chain arrangement available to us changes
the pre-XNU state.

## 13. Evening session: cold init works, the host still does not fetch

### 13.1 The previously successful image tells us the chain, not the trick

`METAL-boot_a.img` (the image the old playbook calls the working configuration) is an
Android v4 boot image whose kernel field is a **raw arm64 Image** of 54,356,304 bytes
and whose ramdisk is empty — byte-for-byte the same layout our `bootshim` build
produces (same `code0=0x14000200`, `text_off=0`, `flags=0xa`, `ARM\x64`).

On today's unit that layout does not boot:

| attempt | result |
|---|---|
| flash raw-Image boot.img to `boot_a`, boot | black screen, then the bootloader |
| 20 KB `hello` image (prints and resets) to `boot_a` | stays in the bootloader, 120 s reset never happens |
| `fastboot boot` the same image | `FAILED (remote: 'No EFI image found in boot.img')` |
| `linuxloader_unlock.efi` in `efisp` + hello in `boot_a` | still the bootloader |
| `fastboot flash boot_a` from the bootloader | `FAILED (remote: 'unknown command')` |

So the raw-Image `boot_a` path is currently unusable on this unit; the documented
chain (`./unixnu bootimg` → `gzip(BootShim + FV)` in the kernel field, payload in the
ramdisk) is the one that has a chance, and a 64 MiB ramdisk makes ABL fall back to
fastboot as well. A PE standalone loader with the payload in the ramdisk remains the
next thing to build (§11).

### 13.2 Cold init: the whole vendor sequence succeeds

With `native-ufs-cold-init=1` and `native-ufs-probe=4`:

```
UFS cold: phy 0xfffffff0570de000 host 0xfffffff0570df000, calibrating
UFS cold: PCS ready (0x400 00000001)
UFS cold: link rc 1, HCS 0000010f UPMCRS 1
NX741J UFS cold: link up rc 1 HCS 0000010f UPMCRS 1 PCS 00000001
NX741J UFS cold: stream 0x60 bypass smr=80000060 s2cr=00000001
```

PHY calibration, SERDES start, PCS ready, HCE and `DME_LINKSTARTUP` all complete.
The UIC result byte is 1 even though `HCS.DP` (bit 0) and `UPMCRS=1` say the link is
up, so the driver now trusts those bits instead of the result byte.

### 13.3 adopt: list installed and started, doorbell returns, host never fetches

```
adopt: enter level=4
adopt: fwList=c3afb000
adopt: list mapped
adopt: doorbell ok hcs=0000010f db=00000000
adopt: list stop loop done rsr=00000000
adopt: base written
adopt: list started hcs=0000010f rsr=00000001
ring-before hcs=0000010f rsr=00000001 dbr=00000000 is=00000004 utrlba=c3afb000 utrd0=11000000 utrd2=0000000f utrd4=c3afc000 ie=00000000
ring-after  hcs=0000010f rsr=00000001 dbr=00000001 is=00000004 ocs=0f
```

With the stream bypass written from the cold-init step (the `mapPhys` of the SMMU
window fails for anything larger than one page, so the bypass is written there with
`ml_io_map`), the doorbell store returns instead of stalling the bus.  `UTRD0` carries
both the UFS-storage command type (bit 28) and the interrupt bit (bit 24), yet the
controller still leaves `DBR` set and `OCS` at `0f`: it never fetches the descriptor.

### 13.4 What this rules out

* the cold-start sequence is not the missing piece — it completes;
* the stream/context state is not the missing piece — bypass is in place and the
  doorbell no longer faults;
* the descriptor is not the missing piece — command type and interrupt bit are set and
  the layout matches `ufshci.h`;
* the queue region is not the missing piece — both our DMA and the bootloader's own
  region behave the same.

What is left is the controller's own request-scheduling state after the firmware has
owned it, which no HLOS-visible register we have tried changes.

### 13.5 Device restored

`boot_a` (stock `91a3f7c1`), `boot_b` (stock, untouched), `efisp` (stock
`4df18359`) and `misc` (zeroed BCB) were restored over 9008; Android boots again.

### 13.6 GCC branch writes are not usable from the kernel

To test whether the controller's DMA master was simply clock-gated, the cold-init step
force-enabled the UFS GCC branches (AXI `0x77018`, AHB `0x77024`, UNIPRO `0x77068`,
aggregate AXI `0x770e4`, bank at `0x100000 + 0x77000`) and printed them before and
after.  The boot stops right after `UFS cold: PCS ready`: the device hangs on those
writes, so the GCC branch state cannot be changed from HLOS on this unit.  The block was
removed again and the firmware/boot chain restored.
