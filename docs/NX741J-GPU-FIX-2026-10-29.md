## 17. 2026-10-29 13:00–14:25 —— GPU 驱动修好的最后两个根因（vktest 实测）

### 17.1 步骤 3.4 终于跑通：用官方 `sweetexecswap` 跑 vktest

launchd 方式装 `vktest` 无效（文件不落盘、daemon 不执行）。正确做法是项目自带机制：

```
sweetexecswap=bluetoothd:/usr/bin/vktest
```

即用内核的 exec-swap 把某个开机必启的守护进程替换成 vktest，输出直接进内核日志。
注意：**被替换的进程必须在 `disabled.plist` 里是启用的**（我们原来禁用了 bluetoothd，
所以替换不触发；把 `com.apple.bluetoothd` 改成 `false` 后才跑起来）。

### 17.3 根因：ring 写指针覆盖未消费命令

`gpu_submit()`（`bsd/dev/pandora_gpu.c`）每次提交往 ring 写约 40 个 dword，
**但从不检查 `CP_RB_RPTR`**。ring 只有 32 KiB（8192 dword，约 200 次提交一圈）；
一旦 GPU 落后，写指针追上未消费命令 → CP 停死 → 之后所有 fence 永不完成
（表现：画面卡住、GPU 仍 1050 MHz 满载发热）。

**修复**（页面「ring 推进 / fence 卡住时仍会失效」）：

```c
static void
ring_wait_space(uint32_t need)
{
	const uint32_t total = (uint32_t)(gpu_bufs[0].bytes / 4);
	for (unsigned spin = 0; spin < 2000; spin++) {
		const uint32_t rptr = gr(CP_RB_RPTR) % total;
		const uint32_t used = (ring_wptr + total - rptr) % total;
		if (used + need + 8 < total) {
			return;
		}
		delay(1);
	}
	printf("PANDORA GPU: ring full (wptr %u rptr %u need %u)\n", ring_wptr, gr(CP_RB_RPTR), need);
}
```
在 `gpu_submit()` 开头调用 `ring_wait_space(96);`。

### 17.5 现在剩下的问题不在 GPU 渲染

GPU 渲染已验证正确且稳定，剩下的用户可见问题属于**合成/呈现路径**：

| 现象 | 归属 |
|---|---|
| 锁屏/桌面壁纸纯色 | CARenderServer 合成未走 GPU（publish 模式 / CA 路径） |
| 快速滑动时画面异常 | 呈现与帧同步（CPU 拷屏 vs GPU 提交） |
| 设置 About 卡死 | MobileGestalt 查询（与本问题无关） |
| 相册闪退 | 上层依赖（AssetsLibrary/媒体），需在其上继续验证 |

### 17.6 关键经验

1. **vktest 必须先跑通**：它把「GPU 算错」和「显示链路错」彻底分开。
2. **exec-swap 的宿主进程必须启用**：禁用列表里的进程不会被替换。
3. **ring 空间检查不能省**：短时间正常、长时间必挂，容易被误判为「GPU 偶发故障」。
4. **`[bo pool]` 行很有用**：能立刻排除「内存泄漏/池耗尽」这类误判。
