# Status — 2026-11-17 (build chain restored; queue ownership proven; fetch still stalls)

## Build chain: three defects fixed

The kernel tree had to be rebuilt from scratch on 11-17, which exposed three
problems that had been masked by a previously seeded tree:

1. **`patches/xnu/0022-sweet-ufs-port.patch` was CRLF.** The driver body was
   extracted from the reference patch with `\r\n`, so `git apply` rejected the
   `bsd/conf/files` hunk on a pristine tree (`patch does not apply`).  The patch
   is now written with LF only.
2. **`xcrun` resolved to the system x86 toolchain.** `/usr/bin/xcrun` maps to
   Ubuntu clang 21 (x86_64), which cannot assemble Mach-O arm64.  A shim at
   `/opt/work/shim/xcrun` now maps every tool to
   `/opt/work/unixnu-linux/CommandLineTools/usr/bin/<tool>` and answers
   `--show-sdk-path` with `/opt/work/nx741j-build/UniXNU/macosx`.
3. **`build/software-aes/libSoftwareAES.a` was a seed artifact.** This board does
   not select the SoftwareAES component (`board.toml` explains why: NativeAES
   duplicates the prelinked IOAESAccelerator), yet `XNU_NATIVE_AES=1` still makes
   the link force-load that archive.  A valid archive containing one stub object
   satisfies the linker; the kernel takes the prelinked provider as intended.

Also added: `configs/no-native-aes.config`, appended last to
`[kernel].config_fragments`, so the device's own `CONFIG_XNU_NATIVE_AES=n`
(`configs/nx741j_defconfig`) is not overridden by `arch:configs/common.config`.
Note `profiles.resolve_path` only understands the `arch:`/`soc:`/`os:` prefixes;
a device fragment must be a plain path relative to the device repository.

With those three fixed, `./unixnu kernel` builds a 53,460,992-byte kernel from an
empty tree, and `./unixnu payload` needs `CROSS_EXTRA_FLAGS=''` because clang 24
rejects `-fptrauth-function-pointer-type-discrimination` for
`--target=aarch64-none-elf`.

## Device results (payloads built tonight)

Probe results are printed with `panic()` (large font) — the console text is
unreadable on this panel.

**Queue ownership is proven twice** — the host accepts our UTRLBA and reads it
back:

```
NX741J UFS step1
want=b4a07000
got=00000000b4a07000  rsr=00000001  e=0
```

```
NX741J UFS step1
want=c3af9000
got=00000000c3af9000  rsr=00000001  e=0
```

(the second one points the list at the **bootloader's own region**, to test
whether the stall is an address-window problem.)

**Reusing the bootloader region through `ml_io_map` is not usable**: the driver
fills packed UTRD/UCD structures with unaligned 64-bit stores, and a device
mapping faults on them:

```
Unaligned kernel data abort, pc 0xfffffff0079ca6e4, esr 0x96000021 (alignment)
far 0xfffffffbbf5f1040        (ml_io_map(0xc3af9000) + 0x1040, the UCD page)
```
