## 八、已知陷阱（踩过的坑）

1. **并行日志会吃掉错误行**：`-j32` 下 `error:` 会与其它输出交错；用 `EXTRA_MAKE_ARGS=-O` 而不是降 jobs。
2. **`-Wno-error` 救不了硬错误**：过度对齐数组、`*void*`（C++）都是 hard error。
3. **format 2 不应用 kit 补丁**：`kits/*/patches/*.patch` 只在 format 1 的 shell 循环里被应用。
4. **陈旧缓存**：`.cache/libpthread-work`、`build/xnu/ios-obj` 会在改 pin 后继续用旧源码/旧对象。
5. **`local.toml` 的本地覆盖会让 status 永远报 `not reproducible`**：验证 pin 时先移开。
6. **9p 上不要编译**；E: 只放仓库，构建在 ext4。
7. **离线取新源**：先播种 `/opt/ghcache`，再 `unixnu fetch`；fetch mu_basecore 子模块时需要
   `GIT_CONFIG_COUNT=1 GIT_CONFIG_KEY_0=protocol.file.allow GIT_CONFIG_VALUE_0=always`。
8. **`vfs_getvfs_with_vfsops` 一类符号**：原始 kernelcache 里有、开源树里没有，需要按需回移。

## 本轮修的两个问题

1. **`board.toml [bootimg.image]` 的数值类型**：`base/kernel_offset/tags_offset` 写成了
   `"0x80000000"` 字符串，`bootimg.verify()` 里做整数加法直接 `TypeError`。
   改成 TOML 整数（`0x80000000` 不加引号），并删掉未生效的 `kernel_compression`（不在
   `MKBOOTIMG_FLAGS` 里）。
2. **`local.toml` 的 `ramdisk = "none"` 会吞掉 payload**：`cmd_bootimg` 见到 `ramdisk` 参数是
   `"none"` 就既不读 payload 也不报错。要带 payload 就注释掉该行（或显式
   `--ramdisk payload.img`）；要对照旧格式就用 `--ramdisk none`。

## 尚未消除的风险（上机前必须确认）

`board.toml` 原有注释记录：**本机 ABL 不接受 gzip 流之后追加的 DTB，也不接受内置 ramdisk**；
而 `unixnu bootimg` 无条件把 DTB 追加在 gzip 之后，标准产物还把 payload 作为 64 MiB ramdisk。
旧的已验证镜像是 ramdisk=0。因此：

- `boot-noramdisk.img` 更接近已验证格式（但仍带追加 DTB），可作为第一个刷机候选；
- 若 ABL 仍拒绝，需回到 payload 另行投放的路径（efisp / userdata FAT / FV 内嵌），
  即 `[partition_strategy]` 里的 B/C 方案。

## 下一步

1. 用 `boot-noramdisk.img` 做一次 `fastboot boot` 冒烟，抓 ABL/UEFI 日志；
2. 确认可用后再决定 payload 的投放方式；

# 补充：boot_a 刷机改走 9008（2026-11-07 11:05）

用户决定：**今后 `boot_a` 一律用 9008 刷**，adb/root 的 `dd` 只作 Android 可用时的应急回滚。

## 链路（已固化成脚本）


所以 9008 只负责"载入 devprg + 跳 fastboot"，真正写分区交给 fastboot —— 与官方救砖包
`flash_all.bat`（清一色 `fastboot flash ...`）的做法一致。

# 更正：9008 裸写 boot_a 的正确姿势（2026-11-07 11:10）

上一节"9008 → fastboot"的结论**不准确**：`reset_to_fastboot` 只是最后手段，官方工具箱其实
**直接在 9008 里裸写分区**。真正的流程在

## 关键差异

| 步骤 | 之前用错的写法 | 工具箱的正确写法 |
|---|---|---|
| 配置 | 没有单独配置，靠 fh_loader 隐式 `<configure>` | 先 `qcedlcmdhelper -p COMx -m xml -f configure.xml`，XML 里带 `Oem="ZTE"` |
| 写入 | `fh_loader --sendxml=w.xml`（无 `--skip_config`） | `fh_loader --sendxml=program.xml --skip_config --showpercentagecomplete --noprompt` |

`Oem="ZTE"`，devprg 直接回 `ERROR: Tool doesn't come from ZTE`。这就是 11-06 那次失败的根因。

## 2. 启动链路

- ✅ `boot_a` = gzip(BootShim+FV)、无 ramdisk、无追加 DTB 时，UEFI 能起（屏幕日志到
  `initstub: entry (BDS=0x1F5E10)`、`EFI_KERNEL_PROTOCOL Install -> Success`、`SmemStubDxe … Success`）；
- ❌ `boot.img` 带 64 MiB ramdisk：slot 健康时干净复测仍回退 fastboot → **ramdisk 路线不成立**；
- ❌ `boot.img` kernel 放 `MZ` PE（LinuxLoader 的 `Booting EFI image` 分支）：三次实验（含纯忙循环探针）
  全部掉 `QUSB_BULK` dump → 分支未执行/`LoadImage` 失败 → **放弃**；
- ✅ Android 侧本身可正常启动（多次恢复后验证）。

## 3. 新增硬约束：metadata 与 userdata 成对重建

全量恢复会重写 `metadata.img`（旧 FBE 密钥）；若 userdata 是后格式化的，Android 会
`vold` 挂载失败 → `volume-failed` → ABL 以 `kmparam.mode=recovery` 无限进 TWRP。

修复（已验证两次）：

```powershell
fastboot reboot fastboot
fastboot format:f2fs metadata
fastboot format:f2fs userdata
fastboot reboot
```

## 4. slot-unbootable 观测

- 每次 boot.img 引导失败即置 `yes`；一次成功引导（或进一次 recovery）后会回到 `no`（后者未做控制实验）；
- 该标志不在 `misc`/`devinfo`/`frp`/`ztecfg`/`uefivarstore`/`secdata`/`ssd`（与 10.24 备份逐字节一致时仍可能是 `yes`）；
- 操作规范：**试前记录、失败后复读，必要时走一次 recovery 或重新进 9008 再读**。
