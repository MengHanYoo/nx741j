## 1. A UFS command completed for the first time

With `native-ufs-cold-init=1` and `native-ufs-probe=4` (the adopt path that reuses
the firmware's request list) the first TEST UNIT READY finished:

```
NATIVE_UFS adopt: TEST UNIT READY lun0
ocs=0 resp=00 scsi=00
phys=c3afc000 hcs=0000010f->0000010f
is=00000005 db=00000000 rsr=00000001
```

`ocs=0` (success), `resp=00`, `scsi=00`, `db=0` (the doorbell was consumed).  This is
the first completed UFS command on this unit and it settles the earlier "the host never
fetches" question: with cold init and the stream bypass in place, the host does fetch.

## 2. Own DMA is not reachable by the controller

The same command through the `sweet_ufs` personality (own `kmem_alloc_contig` buffer at
`0xb4a09000`, same bypass, same cold init) still leaves the doorbell set:

```
NX741J UFS: takeover rc=0 utrlba=b4a09000 rsr=00000001 dbr=00000000
SWEET UFS: ringed cmd 0x1b dbr=00000001
```

So the host only fetches requests from the firmware's own queue region
(`c3afa000`/`c3b03000` etc.).  The adopt path is therefore the only usable one.

## 3. The clocks were never the problem

Read with the SM8850 offsets from data-a-live's `pandora_ufs_clocks()` (the driver's
SM8550 header uses different offsets — writing those hung the unit):

```
SM8850 GCC offsets gdsc=fa22f800 axi=08000001 ahb=08000001 unipro=08000001 aggre=08000001 ice=08004001
```

Every branch enable bit is set.  The earlier "GCC writes hang the device" was a wrong
offset, not a hardware limit.

## 4. The official guide explains the earlier hangs

`porting/ufs` says: *"轮询时不要阻塞。核心没有登记空闲退出延迟时，两次轮询之间的 IODelay
会阻塞在定时器上"*.  The driver waited with `IODelay(1)` in four places, so a command
that did not complete stalled the CPU in the timer path instead of timing out.  All of
them now use a bounded busy-wait, and commands return.

## 5. Data phase returns zeros

`probe=9` (GPT survey) now reaches the read and fails on the capacity data:

```
NATIVE_UFS gpt: unexpected LUN0 block size 00000000
```

The command itself completes (no stall), but the 8 bytes the device sends are not in the
buffer at `phys + dataOffset`.  The adopt path maps the firmware region through
`IOMemoryDescriptor::withPhysicalAddress` and cleaned it by virtual address; data-a-live's
driver always cleans by physical address (`flush_dcache64(pa + off, len, TRUE)`).  The
current build does the same (five call sites) and is flashed; the result is pending.

## 7. 2026-11-19 evening — known-block read and GPT parsing reached

The two remaining data-phase questions from the morning were solved:

* the adopted request list works when the kernel window covers it: DarwinBoot now
  prefers a free run that contains `0xC3B00000`, falls back to the plain allocation
  (QEMU), and reports a covered range up to `0xD0000000` so `arm_vm_init` accepts the
  firmware queue region (`illegal PA 0xc3b…` is gone);
* the data phase needed a correctly built UTRD: with `u7=0x01000001`, `prd0=phys+6144`,
  `prd3=7` and the stream bypass in place, `READ CAPACITY` returned real bytes and
  `resid=0`.

With that, a READ(10) of LBA 1 returns the GPT header and a READ(10) of LBA 2 returns
the entry array:

```
NATIVE_UFS gpt:  done=1 sig=4546492050415254 cur=1 entlba=2 cnt=32 esz=128
NATIVE_UFS gpt2: hdr=1 ents=1 entlba=2 cnt=32 used=12 userdata=11
                 first=4a6328 last=ed4f7fa n0=73736400
```

`first=0x4a6328` is 4,875,048 — exactly the `start_sector` the vendor `rawprogram0.xml`
gives for `userdata` — and the first entry's name bytes decode to `ssd`.  Official
completion conditions 3 (command completion) and 4 (known-block read) are therefore
met, and the partition table matches the Android side.

Next: read the first block of `userdata` (LBA 4,875,048) to locate the root volume
window, then the storage policy (RootLayout / root IOMedia) from the official UFS page.

## 9. Analysis — production transport vs this board (docs + data-a-live)

Official pages read for this note: `/zh/porting/ufs`, `/zh/concepts/boot-chain`,
`/zh/concepts/payload`, `/zh/concepts/prelink`, `/zh/concepts/userdata`, and the
reference port `github.com/yechenan/data-a-live` (`PLAN.md`, `device/DT_FINDINGS.md`).

**What the official component assumes.** ShengUfs takes the controller over from
firmware ("请求队列所有权"), and `RootTransportLayout.h` describes region A as one
contiguous, cached allocation: slot 0 keeps UCD at 4096 and data at 8192 with
`kDataMax = 128 KiB`, so a one-slot region is 136 KiB. A dedicated list page is
optional ("its own page when the port gave it one … else region A's offset 0").
`SmmuTakeover.h` maps the stream's context, `RootCommands.h` owns descriptors and
completion.

**What this board does.** Writing our own list address (measured:
`UTRLBA = 0xb4a09000`) sets the doorbell but the controller never fetches the entry
(`dbr` stays 1); the only list it fetches is the firmware's (`0xC3B0xxxx`). The SMMU
window for a full context is also unusable here (TZ/xPU), so the stream is forced to
match and bypass (`SMR[0]=0x80000060`, `S2CR[0]=1`). data-a-live's unit is the same
shape: its `DT_FINDINGS.md` records `UTRLBA=0xc25b1000` (the bootloader's table), and
its driver works on that table.

**Consequence.** Region A cannot be the 136 KiB allocation on this board; it has to be
the 16 KiB firmware region, which forces `kDataMax = 8192` (one slot = 16 KiB) — a
deviation from the documented layout, and exactly where `hostNop()` now fails: the
step trace stops at "step nop" (before the result print), i.e. the first command that
uses the re-shaped slot/list mapping.  Note also that the NOP trace patch itself is a
candidate for a self-inflicted control-flow error; it must be re-checked before the
next hardware run.

**Two honest routes.**

1. *Board-specific transport (data-a-live's precedent).* Keep cold init + the adopt
   path that is already proven end-to-end (TUR, READ CAPACITY, GPT header, GPT entries,
   `SHNGROOT` manifest), and implement the official root policy on top of it:
   GPT → userdata manifest → SHA-256 over [0,4064) → bounds/window checks → publish the
   OS and SystemOS windows as IOMedia. This is a deviation from the component's
   transport, not from its policy, and it matches what the reference port did.
2. *Make the official transport fit.* Keep the firmware region as region A but shrink
   the slot geometry so entry/list/UCD/data all live in 16 KiB and re-verify the entry
   index rule (2·slot when the list shares region A) and the cache maintenance by
   physical address; only then re-enable `hostBringUp`.

Recommendation: route 1 first (it unblocks condition 5 now), then revisit route 2 as a
cleanup so the device eventually ships the official component unchanged.

existing `probe=12` publication path with progress lines.

Status:

* the patch applies per file when the target is named explicitly (GNU patch 2.8 does not
  resolve the `a/` `b/` headers on this tree), and the resulting driver compiles;
* the build hook that applies it (`scripts/patch-native-ufs-cold-init.py`, self-contained)
  is **not wired into `board.toml`** yet: the probe dispatcher references

  declarations (or the helper must move above the dispatcher). With the hook removed the

* the tree step appears to keep an already-patched driver when it is re-run, so a truly
  pristine baseline for regenerating the diff has to come from the pinned component
  directory rather than from `out/…/tree`.
